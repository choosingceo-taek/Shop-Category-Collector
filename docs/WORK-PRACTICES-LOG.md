# 작업 관행 사례 기록 (CLAUDE.md에서 이동, 2026-11-18)

> 각 관행이 생긴 사례와 실측값. 규칙 자체는 CLAUDE.md에 남아 있다. 비슷한 결함을 다룰 때 grep으로 참조한다.

- **반쯤 긁고 성공이라고 말하는 것이 가장 나쁘다**(v2.8.0, 생성 탐색 2라운드
  `harden-probe`). 라이브 몰 없이 두 가지를 실측했다 — **스크롤로 타일을 내주는 그리드**와
  **거부하는 상품 페이지**.
  - **48개짜리 그리드에서 16개만 걷고 ✅로 채점했다.** 엑셀이 온전해 보이므로 아무도
    모른다. 원인이 셋이었다: ① 스크롤이 **문서 맨 아래로 점프**해서, 그리드 밑에 긴
    푸터처럼 높은 것이 있으면 **트리거를 지나쳐 버린다**(그 뒤로 영영 안 걸린다)
    ② 한 번 지나치면 **다시 훑지 않는다** ③ 몰이 적어 둔 **"48 items"를 못 읽었다** —
    요소 텍스트가 붙어서 `New In48 items`가 되는데 패턴이 단어 경계를 요구했다
    (가격이 이름과 붙던 것과 **같은 종류의 실패**다: 답도 같다 — **그 말을 하는 가장
    작은 요소에서 읽는다**).
  - 고친 뒤: **한 화면씩 내려가며** 훑고(트리거가 뷰포트를 통과한다), 몰이 "더 있다"고
    말하는 동안 **맨 위로 돌아가 다시 훑는다**(최대 4회 · 60개 상한과 라운드 예산이
    끝을 보장). 결과 **16 → 48**. 이미 다 그려진 그리드는 자라지 않으므로 **비용 0**
    (3개 몰 실측 16.1초, 변화 없음).
  - 그래도 부족하면 **화면이 숫자로 말한다**: "이 페이지는 48개라고 적어 놨는데 24개가
    들어왔다 — 그리드가 나머지를 안 내줬다"(⚠️). 조용한 ✅는 이제 불가능하다.
  - **429는 기다리면 답이 달라지는 유일한 거부**다. 평범한 몰은 상품 1개당 PDP 1회라
    60번을 연속으로 두드리는데, 중간부터 throttle이 걸리면 **원단 열이 그때부터 빈다.**
    이제 **한 번만 참을성 있게 재시도**하고(1.5초), 그래도 거부하면 밀어붙이지 않는다.
    그리고 문장이 **상태 코드를 말한다**: "no fabric on any of the 12 — the shop's
    product pages answered 429 (too busy), so scan it again later." 원단이 빈 이유가
    몰의 혼잡인지·거부인지·원래 안 적혀 있는지에 따라 **고칠 사람이 다르다.**
  - `harden-e2e` 8건(수정 전 코드에서 4건 실패 확인).
- **보고를 기다리지 않는다 — 모양을 생성해서 결함을 찾는다**(v2.7.0, 사용자 요청
  "목표를 달성할 때까지 알아서 개발하는 방법"). 이 프로젝트의 결함은 **전부** 디자이너가
  화면에서 발견해 보고하는 경로로 왔다. 그런데 쇼핑몰은 브랜드가 아니라 **독립적인
  선택들의 조합**이다 — 사진을 그리는 방식 × 돈을 쓰는 순서 × 이름의 위치 × 타일 중첩 ×
  상품 주소 모양 × 타일 안 잡동사니 × 페이지 문맥. 선택이 독립적이므로 **결함도
  조합에서 난다**: 색상 칩 버그와 유로 버그는 브랜드를 테스트해서는 절대 못 찾고
  **조합을 테스트해야** 나온다.
  - `matrix-probe.js`가 그 조합을 **생성**한다: 각 축의 모든 값을 기준선에 대해 한 번씩,
    그다음 결정적(무작위 아님) 샘플로 전체 조합 — 지금 **134개**. 실제 크롬에 확장을
    올리고 리더를 그대로 돌린다. 라이브 몰이 필요 없다 — **리더를 깨뜨리는 것은
    마크업이고, 마크업은 생성할 수 있다.**
  - **비어 있지 않음은 정확함이 아니다**(v2.0.0·v2.5.0의 교훈). 셀 값은 페이지가 실제로
    말한 것과 대조한다: 상품 사진(칩·호버컷·저해상도 사본이 아님), 상품명(스크린리더
    문구가 아님), 몰이 쓴 그대로의 가격.
  - 첫 실행에서 **3건**을 찾았다(아무도 보고하지 않은 것들):
    ① **이름 끝의 숫자가 뒤 가격과 붙었다** — "Style Number 1" + "89,00 €" →
    **`189,00 €`**. 마크업은 두 노드 사이에 공백을 안 넣으므로 감싸는 요소의 텍스트가
    한 덩어리로 읽힌다. 이제 **가격을 품은 더 작은 요소가 있으면 그쪽을 쓴다**
    (501·Air Max 90·Tee 2.0처럼 숫자로 끝나는 이름은 흔하다).
    ② `/p/style-number-1/PROD1.html` → 상품명 **"Prod1"**.
    ③ `/product.do?pid=901` → 상품명 **"Product.Do"**. 주소에서 이름을 꺼낼 때
    **마지막 조각을 무조건** 쓰고 있었다. 이제 뒤에서부터 훑으며 **라우팅 단어·파일명·
    불투명 코드**를 건너뛰고, 사람이 읽으라고 쓴 조각(구분자가 있는 것)을 고른다.
    아무것도 없으면 **빈 칸**이다 — 지어낸 이름은 빈 칸보다 나쁘다(LAB이 단어로 센다).
  - **축을 늘리는 것이 곧 개발 계획이다.** 새 값을 하나 추가하면 그 값이 실패에 몇 번
    나타나는지 표로 나오고, 그게 다음에 고칠 것이다. `matrix-e2e.js`는 같은 생성기를
    계약으로 고정한다(HEAD에서 134개 중 **7개 실패** 확인).
  - **목표 문장 자체도 테스트다**: `goal-e2e.js`는 네 가지 몰 원형(Shopify 벌크 JSON ·
    JSON-LD 조성 · 유로 표기+배경 이미지+아코디언 · 그리드에 사진이 아예 없어 PDP가
    채워야 하는 몰)에 **실제 리스트 실행**을 걸고, 모든 행에 **브랜드·상품명·사진·조성**이
    있는지, 브랜드가 사용자가 지은 이름인지, 스캔의 자기 판정이 ✅인지, 그리고 **LAB
    한 화면에 다 보이는지**까지 검사한다. 27건.
- **리스트 실행은 URL마다 엑셀을 만들고 그걸 버리고 있었다**(v2.1.0, 사용자 질문
  "자동으로 building excel하느라 시간이 오래 걸리는 것인지"). 그렇다 — 그리고
  **대부분이 낭비였다.** build 단계가 URL마다 `buildWorkbook`을 호출해 **그 몰의
  썸네일을 전부 내려받아** 워크북에 넣는데, 리스트 실행이면 그 `bytes`를 쓰지 않고
  버린다(파일은 마지막에 `queueExport`가 하나 만든다). 14개 몰이면 **버려질 워크북
  14개 + 사진을 두 번 내려받기**다.
  - 그 코드가 실제로 쓰던 건 `kept`(내보내기 필터를 통과한 행)뿐이고, 그건
    `WPBExcel.filterKept`가 **ExcelJS도 네트워크도 없이** 준다.
  - 실측(3개 몰 × 60개, 이미지 80ms): **33.3초 → 16.1초**, 이미지 요청 **426 → 242**.
    14개 몰 기준 **약 2.6분 → 1.3분**.
  - **상품은 엑셀과 무관하게 몰마다 카탈로그에 들어간다**(`catalogSave`가 URL마다
    호출됨) — 엑셀을 안 뽑아도 PRODUCTS·LAB에는 이미 들어와 있다. 중간에 Stop해도
    그때까지 분은 남는 이유가 이것이다.
  - **재스캔은 옛 사진을 덮어쓴다**(`store.merge`): 새 값이 비어 있지 않으면
    이긴다. 다만 **재스캔 전까지는 옛 주소가 그대로 남으므로**, 주소가 깨져 있던
    몰(v2.0.0)은 한 번 다시 스캔해야 사진이 나온다.
- **실행 속도는 측정해서 줄인다**(v1.96.0, 사용자 요청 "14개 브랜드가 시간이 많이 든다").
  추측 대신 계측했다(`speed-probe.js` — 3개 몰 × 상품 60개, PDP 응답 250ms):
  **몰당 10.7초 중 상세 단계가 7.8초**였고 그 대부분이 *기다리는 시간*이었다.
  - **레인 4 → 8.** 상세는 순수 네트워크 대기라 탭이 놀고 있었다. 8은 브라우저가
    몰 페이지 하나에 여는 연결(호스트당 6 + 프리커넥트)보다 여전히 적다.
  - **URL 사이 대기 1500ms → 400ms.** 콜백이 나갈 시간만 있으면 되는데 URL마다
    1초를 버렸다 — 팀 리스트면 20초.
  - **스크롤 안정성 확인 700ms → 450ms.** 규칙은 그대로(개수·높이가 두 번 안정),
    보는 간격만 줄였다. 이미 다 그려진 그리드가 매번 2초를 증명에 쓰던 것이 절반이 된다.
  - **이미 있는 사진 때문에 PDP를 열지 않는다**(`readDetail(a, url, repaired, have)`).
    v1.94에서 "사진이 없으면 PDP" 규칙을 넣었는데, 판정을 *상세 결과*로만 해서
    타일이 사진을 준 행도 페이지를 열었다.
  - 결과: **32.2초 → 18.2초**(3개 몰). 14개 몰 기준 **약 2.5분 → 1.4분**.
  - 더 못 줄이는 부분: 몰이 응답하는 시간 자체. generic 몰은 상품마다 PDP가
    유일한 원단 출처라 요청 수를 줄일 수 없다(Shopify는 벌크 JSON 한 번으로 끝난다).
- **사진이 안 보이는 세 번째 원인은 권한이다**(v1.96.0, 사용자 재보고 "aritzia·
  lululemon·adidas·vuori 여전히 안 보인다"). v1.94가 워커로 다시 받게 했지만
  **워커도 우리가 가진 호스트만 받을 수 있다.** 대부분의 몰은 자기 도메인의
  서브도메인에 사진을 두지만(`images.lululemon.com`·`assets.adidas.com` ✅),
  **Aritzia는 Adobe Scene7**(`aritzia.scene7.com`)이고 Cloudinary·Amplience·
  Contentful도 흔하다 — **우리 목록이 그걸 다 적을 수는 없다.**
  → 이제 워커가 **왜 실패했는지 구분해서 답한다**: 권한이 없으면 `need: origin`.
  LAB은 그걸 모아 밴드에 **"Show these photos" 버튼**을 띄우고, 클릭 안에서
  `permissions.request`를 한다(크롬의 제스처 요건). 매니페스트에 CDN을 계속
  추가하는 대신 **모르는 몰에도 통하는 길**이다.
- **왜 매번 사용자가 먼저 발견해야 했나**(v1.95.0, 사용자 지적 "이런 것들을 왜 내가
  직접 언급을 해야 수정하는거야"). 이 프로젝트의 결함은 **전부 같은 경로**로 왔다 —
  디자이너가 LAB을 열고, 드롭 이름으로 쪼개진 브랜드나 회색 카드 60장이나 빈 원단
  열을 보고, 말해 준다. **그게 진짜 버그였다.** 원인은 셋이고 셋 다 고쳤다:
  - **① 검사가 깨지는 것을 안 봤다.** Set Active는 **✅였다** — 모든 행에 이름·사진·
    가격·조성이 있었으니까. "한 몰이 한 브랜드인가"를 아무도 안 물었다. 원단은
    전무(全無)일 때만 ⚠️라 **60개 중 3개도 건강**으로 통과했다.
    → `saidBrands`(몰이 스스로 말한 브랜드, 리스트 이름을 덮어쓰기 **전**)를 기록하고,
    `multiBrand`가 아닌데 이름이 여럿이면 ⚠️. 원단·사진은 **비율**로 본다
    (`THIN_FABRIC 0.25` · `THIN_PHOTO 0.5`). `health-test` 21건.
  - **② 판정이 아무도 안 보는 곳으로 갔다.** VUORI는 **제대로 잡혔었다**(사진 0/60).
    그런데 그 사실은 서비스워커 콘솔의 `devsitecheck()`에만 있었다. 디자이너는 그걸
    영원히 치지 않는다 — **도구가 알고 있어도 아무 가치가 없다.**
    → 판정을 **사람이 읽는 문장으로 스캔 시점에 써 두고**(`rec.why` —
    "VUORI: no photos at all (60 products)") **LAB 상단 밴드**에 띄운다. 깨끗한
    스캔이면 **아무것도 그리지 않는다**(높이 0 — 컴팩트 예산 유지). `selfcheck-e2e` 8건.
  - **③ 스캔이 있는 곳에서 안 보이는 결함이 있다.** 표시할 때만 실패하는 사진
    (nike·lululemon)은 수집 시점엔 정상이다. LAB이 그걸 세어 **같은 밴드에** 넣는다.
  - 규칙: **새 결함을 고칠 때는 "이걸 도구가 스스로 말했겠는가"를 먼저 묻는다.**
    아니라면 고칠 것이 둘이다 — 그 결함과, 그것을 못 본 검사.
- **사이트 진단은 스캔이 스스로 한다**(v1.67.0, 사용자 요청 "diagnose js 수동
  확인이 아니라 그 부분도 자동화"). 사이트 뚫기의 수동 단계는 "파일 하나 보내기"만
  남는다.
  - **모든 스캔이 URL마다 판정을 기록**한다(`wpb_sitehealth`, collectionSig 키,
    최근 300개): 상품 수 · 이름/사진/가격/원단 채움 수 · 엔진 · ✅/⚠️/❌. build 단계
    진입 시 `recordHealth()`가 쓰고, 실패해도 스캔은 절대 안 죽는다(전부 래핑).
    **원단은 전무(全無)일 때만 ⚠️**(`fabric×all`, withSpec 실행에 한함) — 개별 상품이
    조성을 안 밝히는 건 정상이지만 사이트 전체 0은 추출이 깨진 것이다. 이때는
    상품 페이지 1개도 자동 촬영한다(`diagnoseDetail`): PDP의 JSON-LD 타입·material,
    본문의 `숫자%` 문장 실물 최대 4개, Shopify `.js`의 description 길이·% 개수.
    diagnose-pdp.js가 손으로 하던 그 확인이다(Edikted·Alo가 계기).
  - **실패한 사이트는 그 자리에서 자동 촬영**(`selfDiagnose()`): 플랫폼 마커 ·
    JSON-LD 타입 요약 · 링크 경로 모양 상위 6개(숫자→N 접기) · 반복 그리드 후보 ·
    이미지 lazy 속성 분포 · 가격 leaf 수 · 실제 타일 1개(1.4KB 상한, 전체 4KB 상한).
    diagnose-generic.js가 손으로 모으던 사실들이다. ✅는 촬영하지 않고, 페이지네이션
    으로 스캔한 페이지를 떠났으면 엉뚱한 페이지를 찍지 않도록 건너뛴다.
  - **막히면 페이지를 직접 읽고 스스로 고친다**(v1.79, 사용자 요청 "확장 프로그램이
    알아서 F12에 들어가 사이트 구조를 파악해서 반영"). 진단은 *말해 주는* 데서
    끝났는데, 리스트가 빈 엑셀로 돌아온 디자이너는 정규식 한 줄이 고쳐질 때까지
    도구가 고장 난 상태로 기다려야 했다. 이제 어댑터가 0을 내면 **구조 리더
    (generic)로 페이지를 읽어 그걸 수집한다** — 우리의 낡은 규칙보다 몰의 마크업이

    안 돌아오면 **이미 복구 화면을 보고 있다**(사라진 확장을 찾아 헤매지 않는다). `oneclick-e2e` 19건(실제 `FileSystemDirectoryHandle`에 기록·껍데기
    제거·하위 폴더 생성·deflate 원본 일치·거부 케이스) · `redownload-e2e` 18건.
- **다시 받는 것이 곧 업데이트다**(v1.85.0, 사용자 요청 "자동 업데이트가 어려우니
  다시 다운로드할 수 있도록"). 크롬은 **직접 로드한 폴더를 절대 갱신하지 않는다**
  — 디스크의 파일이 곧 확장이다. 그래서 재다운로드는 우회로가 아니라 **정규 경로**이고,
  채팅 메시지 속 링크가 아니라 패널 안 한 곳에 있어야 한다.
  - 헤더의 **버전 칩**(`v1.85.0`, 기존 줄이라 **높이 비용 0** — 테스트로 측정)을
    누르면 **번호 붙은 3단계**가 열리고 각 단계에 그 일을 하는 버튼이 있다:
    ① **⬇ Download the latest** → `market-lens.zip`으로 다운로드 폴더에 저장
    (워커의 `chrome.downloads`를 쓰므로 브랜치명이 아니라 알아볼 이름이 붙는다)
    ② 압축 풀어 **같은 폴더에 덮어쓰기**(폴더를 유지해야 리스트·카탈로그가 남는다)
    ③ **Open chrome://extensions** 버튼 → ↻. 확장은 chrome:// 페이지를 열 수 있다
    (추측이 아니라 실측 확인). 열려 있던 쇼핑몰 탭은 스스로 새 엔진을 받는다.
  - 맨 아래 줄이 **지금 어디쯤인지** 말한다: "v1.85.0이 최신" / "v1.86.0이 나왔다" /
    "**이미 폴더에 있다 — 3단계만 남았다**"(update.bat이 이미 돈 경우). `redownload-e2e` 16건.
- **업데이트는 더블클릭 하나 + 리로드 한 번이다**(v1.81.0, 사용자 요청 "그냥 바로
  업데이트되는 편리한 방법"). 확장 폴더 안의 **`update.bat`**(맥은 `update.command`)이
  ZIP을 받아 **같은 폴더에 덮어쓴다** — 압축 풀기·안쪽 폴더 찾기가 사라지고 폴더
  경로가 그대로라 확장 ID·설정·카탈로그가 유지된다(자기 자신은 `/XF`로 제외 —
  실행 중인 배치 파일을 덮어쓰면 나머지 줄이 깨진다).
  - **확장이 디스크를 스스로 본다**: 워커가 5분마다(패널을 열면 즉시) 자기
    `manifest.json`을 fetch해 **실행 중 버전과 디스크 버전을 비교**한다. 다르면
    툴바에 ↻ 배지, 패널에 "폴더에 준비됨 · chrome://extensions에서 ↻ 한 번" 한 줄.
    "새 버전이 있다"와 "새 파일이 이미 폴더에 있다"는 남은 거리가 달라 구분해 말한다.
  - **자동 리로드는 하지 않는다**(측정 결과). `chrome.runtime.reload()`는 unpacked
    확장을 내리고 **다시 올라오지 않는 것을 확인**했다 — 디자이너 브라우저에서
    확장이 사라지는 것보다 클릭 한 번이 낫다. 클릭은 사람에게 남긴다.
  - **F5는 없어졌다**: 리로드 직후 워커가 열려 있는 쇼핑몰 탭에 엔진을 다시 넣는다
    (`reinjectOpenTabs`, 버전당 1회). "Extension context invalidated"의 원인이 이거였다.
  - `selfupdate-e2e` 14건. 진짜 자동 업데이트는 여전히 웹스토어 쪽(`STORE.md`).
